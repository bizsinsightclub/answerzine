# ANSWER ZINE

> **순위 말고, 팔린 이유.**

매주 국내에서 잘 팔린 것들 중에서 **"왜 팔렸는지 설명할 수 있는 것"만 골라** 한 호를 만듭니다.
1위여도 이유를 못 대면 싣지 않고, 7위여도 이유가 선명하면 싣습니다.

한 호가 나오면 **웹 아카이브가 갱신되고, A4 한 장짜리 종이 진이 나옵니다.**
종이의 QR을 찍으면 웹의 전체 글로 이어집니다.

> 이 문서는 사람이 읽는 안내서입니다. 존댓말로 쓰인 문서는 사람용,
> 반말(`-다`)로 쓰인 문서는 에이전트에게 주는 지시문입니다.

## 매주 하는 일

**에이전트가 만들고, 사람은 확인하고 승인합니다.** 직접 채워 넣을 일은 거의 없습니다.

Cowork나 Claude Code에서 이렇게 부르시면 됩니다.

```
1. "az-scout으로 이번 주 4개 도메인 후보를 모아줘"
      → 영화·음악·유튜브·도서를 동시에 훑고 점수를 매깁니다

   ↓ 대시보드를 열어 확인하세요. 점수와 "사람 대기" 항목이 보입니다

2. "az-verify로 상위 후보들을 검증해줘"
      → 숫자와 날짜를 다시 확인합니다. 떨어뜨리는 게 목적인 단계입니다

3. "az-write로 통과한 도메인 스토리를 써줘"
      → 기사 본문을 씁니다

4. "az-editor로 회차를 조립하고 qa를 돌려줘"
      → 1면에 실을 기사를 고르고, 자동 검사를 돌립니다

   ↓ 여기서 Michael님이 최종 승인하십니다

5. "az-retro로 이번 호 회고해줘"
      → 이번 주에 놓친 게 있었는지 정리하고 규칙 추가를 제안합니다
```

각 단계가 끝나면 **대시보드**를 열어 보세요.
어느 도메인이 어디까지 갔는지, 뭘 물어보려고 기다리는지 한 화면에 나옵니다.

```

```

기사 문장을 손보고 싶으시면 **제작기**를 여시면 됩니다.
`JSON 불러오기`로 이번 주 회차를 열면 글자 수와 종이 배치를 바로 확인하실 수 있습니다.

### Michael님이 판단하셔야 하는 것

에이전트가 알아서 하되, 아래 상황에서는 **멈추고 물어봅니다.**

- 부고·사고·질병처럼 민감한 소재가 후보에 올라왔을 때

## 처음 한 번만 하는 설정

### 1. 저장소 올리기

이 폴더를 통째로 GitHub에 올리시면 됩니다.
공개 저장소여야 무료로 웹 주소를 받을 수 있습니다.

```bash
git init
git add .
git commit -m "ANSWER ZINE 초기 구성"
git branch -M main
git remote add origin https://github.com/<계정>/answer-zine.git
git push -u origin main
```

### 2. 웹 주소 켜기

저장소에서 **Settings → Pages → Source**를 `GitHub Actions`로 바꾸시면 됩니다.

이제 파일을 올릴 때마다 자동 검사가 돌고, 통과하면 대시보드와 제작기가 웹 주소로 배포됩니다.
출처 목록을 고치면 다음에 접속할 때 바로 반영됩니다.

> 파일을 더블클릭해서 여시면 브라우저 보안 때문에 저장소 값을 못 읽습니다.
> 화면 위쪽에 `● 저장소` 대신 `○ 내장 기본값`이라고 뜨면 그 상황입니다.
> 웹 주소로 접속하시면 해결됩니다.

```

**데이터 파일**

```

issues/*.json           완성된 회차
runs/*.json             에이전트 작업 기록
```

**도구**

```

### 값을 고치실 때

**같은 값을 두 군데 적지 않습니다.** 카테고리 색상은 `domains/registry.json`에만,
출처 목록은 `sources/whitelist.json`에만 있습니다.
문서 안의 표는 눈으로 보시라고 옮겨 적은 사본이니, 값을 바꾸실 때는 JSON을 먼저 고치세요.

## 자동으로 막아주는 것들

`tools/qa.mjs`가 파일을 올릴 때마다 아래를 검사합니다. 하나라도 걸리면 배포가 멈춥니다.

**날짜와 시장**

- 사건이 일어난 날이 집계 기간보다 늦으면 실패합니다. 그 주엔 아직 일이 안 생겼다는 뜻이니까요
- 본문이 "4주 차"라고 썼는데 날짜로 계산하면 2주 차면 실패합니다
- 국내 기사에 해외 출처를 쓰면 실패합니다. 반대도 마찬가지입니다

**출처**

- 허용 목록에 없는 사이트를 근거로 쓰면 실패합니다
- 블로그·커뮤니티·위키·검색 결과 페이지는 막혀 있습니다

**글과 형식**

- 종이 한 장을 넘길 만큼 글이 길면 실패합니다. 기준은 실제로 인쇄해서 재본 값입니다
- 제목에 물음표나 느낌표가 있으면 실패합니다
- 기사 구조가 정해진 5토막(현상 → 숫자 → 맥락 → 해석 → 마무리)이 아니면 실패합니다

**규칙 관리**

- `LESSONS.md` 형식이 어긋나거나, "자동화"라고 적어놨는데 실제 검사가 없으면 실패합니다

직접 확인해보고 싶으시면 이렇게 하시면 됩니다. 설치할 것은 없고 Node 20 이상만 있으면 됩니다.

```bash
node tools/qa.mjs                      # 전부 검사
node tools/qa.mjs issues/2026-w32.json # 특정 회차만
```

### 이 검사들이 생긴 이유

전부 **실제로 났던 사고**에서 나왔습니다.

시작 단계에서 만든 영화 기사가 국내 개봉 전 주간의 박스오피스 숫자를 인용했습니다.
개봉일을 처음 발표된 7월 15일로 써놨는데, 그 날짜는 나중에 8월 5일로 바뀌었고
미국 개봉일은 또 7월 17일로 달랐습니다. 결국 존재할 수 없는 숫자가 기사에 실렸습니다.

자세한 내용은 `market-scope.md`, 교훈 정리는 `LESSONS.md`의 L-001에 있습니다.

## 배운 것을 쌓는 방식

교훈을 적어두기만 하면 언젠가 잊힙니다. 그래서 **기계가 막게 만드는 것을 목표로** 잡았습니다.

```
사고가 남 → az-retro가 규칙을 제안 → Michael님이 승인
   → "관찰" 또는 "수동" 상태로 등록
   → 규칙이 분명해지면 자동 검사로 구현
   → "자동화"로 졸업              ← 여기가 목표
```

에이전트는 일할 때마다 어떤 교훈을 참고했는지 기록에 남깁니다.
그래서 **3번 넘게 쓰인 "수동" 항목은 자동 검사가 알아서 졸업 후보로 알려줍니다.**
대시보드에서 그 순위를 보실 수 있습니다.

지금은 10건 중 6건이 자동으로 막히고 있습니다 (60%).

## 나중에 필요해지면

지금 구조는 **혼자서, 주 1회, 1년에 56번 정도 파일을 고치는** 상황에 맞춰져 있습니다.
데이터베이스 없이 파일만으로 충분한 규모입니다.

아래 상황이 생기면 그때 백엔드를 검토하시면 됩니다.

- 같이 편집하는 사람이 여러 명이 되어 누가 승인했는지 남겨야 할 때
- 회차가 쌓여서 "이 개념을 쓴 기사 전부 찾아줘" 같은 검색이 필요할 때
- 독자용 웹에 로그인이나 구독을 붙일 때

그때 옮기기도 어렵지 않습니다. 기사는 이미 JSON이고 규칙은 이미 문서로 분리돼 있습니다.
